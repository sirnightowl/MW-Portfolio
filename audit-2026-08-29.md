# Portfolio Engineering Audit

**Project:** Martin Whitaker Portfolio (martwhitty.dev)
**Stack:** Next.js 16 (App Router), React 19, TypeScript 5, Tailwind CSS 3, Vitest, Playwright
**Deployment:** Node-server deployment via `next start` (31 pages prerendered at build (33 HTML outputs including _not-found and _global-error); no API routes, no middleware). Note: `headers()` in `next.config.ts` is only honoured in this deployment mode — under `output: 'export'` static hosting it would be silently ignored.

---

## Executive Summary

This is a static portfolio site with no backend, no database, no API surface, and no user authentication. The attack surface is extremely narrow — the site serves pre-rendered HTML with client-side interactivity limited to a contact form (mailto), a theme toggle, a mobile menu, scroll reveal animations, animated counters, and a click-to-load YouTube facade.

**Engineering maturity:** Good for a personal portfolio. Decisions are deliberate and consistent. The codebase is small enough to hold in working memory, which is appropriate for the project's scope.

**Biggest risks:** None are critical. Remaining lower-priority items are documented in the backlog below. The three highest-value fixes from the original audit have all been implemented: the markdown renderer now uses `react-markdown`, E2E coverage is in place, and `global-error.tsx` catches layout-level errors.

**Production readiness:** High. All pages are prerendered; the Next server serves them with security headers. No runtime database calls. No third-party API dependencies at runtime.

**Security posture:** Strong — no authentication surface, no user data storage, no server-side code. The only `dangerouslySetInnerHTML` usages are controlled JSON-LD injection and a theme-detection script, both safe by inspection. CSP + other security headers have been added as defence-in-depth.

## 1. Hand-rolled Markdown Renderer

- **Status:** Resolved
- **File & Line:** `app/blog/[slug]/page.tsx:71-75`
- **Category:** Maintainability | Reliability
- **Severity:** Medium
- **Confidence:** High

### Resolution

Removed the custom 90-line regex parser and replaced it with `react-markdown` + `remark-gfm`. Added a custom `.prose-ink` theme defined directly in `app/globals.css` that preserves the existing typographic style (bullet colour, numbered list styling, heading sizes, link weight).

```tsx
import Markdown from 'react-markdown'
import remarkGfm from 'remark-gfm'

// ...
<div className="prose-ink mx-auto max-w-2xl">
  {article.body ? (
    <Markdown remarkPlugins={[remarkGfm]}>{article.body}</Markdown>
  ) : (
    <p className="text-lg leading-8 text-ink/65">This article hasn&rsquo;t been published yet. Check back soon.</p>
  )}
</div>
```

This gives full CommonMark + GFM support (headings, paragraphs, lists, links, bold, horizontal rules, tables, strikethrough, task lists) and removes the risk of silently broken HTML.

### Verification

- `npm run build` passes.
- E2E test `blog post renders markdown content` passes.

## 4. Missing global-error.tsx

- **Status:** Resolved
- **File & Line:** `app/global-error.tsx`
- **Category:** Reliability
- **Severity:** Medium
- **Confidence:** High

### Resolution

Added a `global-error.tsx` that matches the visual style of the existing `app/error.tsx`. It logs the error and offers a reset button plus a link back home. Because this boundary catches errors in the root layout, it renders a full `html`/`body` shell.

Caveat: Next.js does not inject the global stylesheet into `global-error.tsx` renders, so Tailwind classes may degrade to browser defaults if the boundary activates before styles load. Since all pages are prerendered, the stylesheet is typically already present on client-side errors; worst case is an unstyled but functional error page.

### Verification

- `npm run build` passes.
- TypeScript accepts the component signature.

## 6. Reveal Component: No Fallback for IntersectionObserver Absence

- **Status:** Resolved
- **File & Line:** `components/common/Reveal.tsx`
- **Category:** Reliability
- **Severity:** Low
- **Confidence:** Medium

### Resolution

Added a guard: if `IntersectionObserver` is unavailable, or the user prefers reduced motion, the component immediately adds the `reveal` class so content shows without animation.

**Follow-up (post-review):** the component was rewritten for progressive enhancement. The hidden state is no longer an inline React style baked into the server HTML — it now lives in CSS, gated behind an `html.js` class set by the inline head script (`html.js [data-reveal] { opacity: 0; … }`). With JavaScript disabled, blocked, or failed, reveal content is simply visible; with JS on, the effect runs pre-paint (no visible→hidden flash) and the IntersectionObserver reveals on scroll.

### Verification

- `npm run build` passes.
- Existing Vitest tests for other components still pass.

## 8. No Content Security Policy Headers

- **Status:** Resolved
- **File & Line:** `next.config.ts:6-28`
- **Category:** Security
- **Severity:** Low
- **Confidence:** High

### Resolution

Added security headers for all routes:

- `X-Content-Type-Options: nosniff`
- `X-Frame-Options: DENY`
- `Referrer-Policy: strict-origin-when-cross-origin`
- `Content-Security-Policy` with directives for `default-src`, `script-src`, `style-src`, `img-src`, `font-src`, `connect-src`, and `frame-src`.

`script-src 'unsafe-inline'` is required for the theme script and JSON-LD; `'unsafe-eval'` is appended only in development (`NODE_ENV === 'development'`), so production ships without it. `object-src 'none'`, `base-uri 'self'`, `form-action 'self'`, and `frame-ancestors 'none'` were added as further hardening. Headers are emitted by the Next server (`next start`) — they would NOT be served under `output: 'export'` static hosting.

### Verification

- `npm run build` passes.
- Headers are emitted in production (verified by serving the production build and inspecting the response).

## Strategic Recommendations (Post-Fix)

1. **Keep `react-markdown` up to date** — it is now a critical rendering dependency. Automate dependency updates via Dependabot or similar.

2. **Run E2E tests in CI** — add `npm run test:e2e` to the deployment pipeline. With the local dev-server setup in `playwright.config.ts`, this is a one-line CI addition.

3. **Revisit CSP tightness** — `'unsafe-eval'` is already gated to development; the remaining `'unsafe-inline'` in `script-src` is required for the theme script and JSON-LD. If CSP ever becomes a hard requirement, move the theme script to an external file and use a nonce. Note headers are served by `next start`; if the site moves to true static hosting, headers must move to the host layer (`_headers`/`vercel.json`).

4. **Execute the MDX migration** when the article count approaches 40 or when code blocks/syntax highlighting become a regular need. The `Article` interface and blog templates are already designed to make this a small change.

5. **Add a README.md** describing setup, scripts, and deployment. This is the one documentation gap that remains.
